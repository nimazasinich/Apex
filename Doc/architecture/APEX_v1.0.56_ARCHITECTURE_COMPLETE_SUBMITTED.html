Failure handling

Why sandbox 403s were non-fatal

Both KuCoin and Binance returned HTTP 403 (exchange_forbidden_or_geo_blocked). The circuit breaker caught it; LKG cache served stale or empty data; health endpoint reported UNAVAILABLE instead of crashing. Strategy catalog and operations status still returned valid JSON.

Proxy routing

Direct / SOCKS5 adaptive routing

proxyFetch auto-probes a local SOCKS5 proxy at 127.0.0.1:10808 if no proxy env vars are set. This is not incidental — it reflects the operator's known DreamMaker VPN/proxy infrastructure. Background and interactive requests use separate concurrency lanes.

Section 8 — Persistence & Governance

L7 — Flat-File JSON Only (No Database Server)

DecisionMemoryMirror · decisionMemoryDatasetSync.ts

DecisionMemoryMirror

Append-only decision log, optionally mirrored to an external dataset. Boot observed: restore status=SKIPPED rows=0 — no mirror currently configured.

AdaptiveThresholdGovernanceStore

Adaptive Threshold Governance

Governs scanner configuration drift over time. Stores threshold changes as JSON. Coupled with MathEngine at L4 by construction.

EdgeThresholdGovernanceStore

Edge Threshold Governance

Governs Liquidity Hunter edge thresholds with explicit propose/approve/reject flow. A threshold change is NOT self-applying — requires explicit operator approval via /api/liquidity-hunter/edge-thresholds/{propose,approve,reject}.

No database: All persistence is flat JSON files on disk under configurable paths. No database server, no Redis, no message broker. This is simple and self-contained but limits horizontal scaling and querying capability.

Not Yet Implemented / Known Gaps

Items below are drawn from deep code audits, live boot observations, and engineering session history. Each item names the exact file or subsystem affected. These are NOT future feature requests — they are gaps in the current codebase that affect correctness, safety, or observability right now.

CRITICAL BUGS — affect correctness silently
01

Scanner Engine Split — Live vs Backtest use completely different logic

The live market scanner in scannerCore.ts uses classic RSI/MACD indicators. The more sophisticated OBI (Order Block Intelligence) / QStruct engine is wired ONLY into the backtesting pipeline. A strategy that passes backtesting cannot be guaranteed to produce comparable live signals because the two engines operate on different analytical logic. There is no warning or disclosure anywhere in the UI.

scannerCore.ts src/services/strategyEngine/ backtesting.ts
CRITICAL
02

Math.min Threshold Override — User configuration silently ignored

A Math.min call in scannerCore.ts permanently caps the final composite score, overriding any user-configured threshold above that cap. Users who set higher thresholds see their configuration silently discarded at runtime. No error is thrown, no log line is emitted.

src/services/scannerCore.ts
CRITICAL
03

replay_proxy Mode — 3 scanner presets always use estimated inputs, never disclosed

Three scanner-preset strategies that use scannerPresetAdapter.ts always run in replay_proxy mode with estimated (not real) inputs. The UI presents these signals identically to signals based on real market data. There is no badge, tooltip, label, or warning anywhere in the frontend that discloses this to the user.

No Horizontal Scaling / Database Layer

APEX is a single Node.js process with flat JSON file persistence. There is no database server, no Redis cache, no message broker. All state (orders, thresholds, decision memory) lives in JSON files on disk. This is intentional for simplicity but means the system cannot run multiple instances concurrently, and recovery from disk corruption requires manual intervention.
